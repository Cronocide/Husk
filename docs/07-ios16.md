# Husk on iOS 16

The target is a **rootless semi-jailbroken iPhone on iOS 16.4–16.6.1 with JIT**
(Dopamine and its kin).

**The app needs no source changes.** That is the headline, and it was not the
expectation going in. Verified on the self-hosted Mac, against the iOS 26.5 SDK
from Xcode 26.6:

```
swiftc -typecheck -target arm64-apple-ios16.4 -import-objc-header Husk/HuskBridge.h \
       Husk/*.swift HuskJITHelper/HuskJITMessages.swift      ->  0 errors
clang  -fsyntax-only -target arm64-apple-ios16.4 <51 translation-layer files>  ->  0 errors
```

What iOS 16 needed instead was the *bundle*, the deployment targets, and a
workflow to build it.

## JIT: nothing to port

`JITBootstrap.canGrantOwnJIT` returns true below iOS 26 — that is where the
Trusted Execution Monitor arrives and takes self-granted executable memory
away. So on iOS 16 the `dynamic-codesigning` entitlement in
`Husk.entitlements` is honoured and `MAP_JIT` simply executes. No debugger, no
hand-off, no breakpoint RPC. The entire substrate described in
[02-jit-substrate.md](02-jit-substrate.md) is machinery for a problem iOS 16
does not have.

The pieces that recognise the device are already there too:

- `JITBootstrap.isJailbroken` tests for `/var/jb`, where a rootless jailbreak
  puts itself.
- `JITBootstrap.noteLaunchState()` reads `CS_DEBUGGED` through `csops(2)` at
  launch, which is what "Allow JIT in Apps" leaves set on every app it starts.
- `JITSetup.resolvedMethod` falls through StikDebug and TrollStore to
  `.jailbreak`, and `JITCard` offers that.

**One thing to confirm on the device**, as the single assumption that could be
wrong: `isJailbroken` only looks at `/var/jb`. If the jailbreak in use roots
itself elsewhere, the JIT card will name the wrong method. It should still
*work* — `debuggedAtLaunch` is read independently and does not depend on
detecting the jailbreak — so the symptom is a confusing card, not a dead app.

## A correction worth recording

The first pass at this branch shimmed two APIs it believed were iOS 17, on the
strength of Apple's documentation:

| API | Documented | Actually, per the SDK |
| --- | --- | --- |
| `MainActor.assumeIsolated` | iOS 17.0 | `@available(iOS 13.0) @_alwaysEmitIntoClient` |
| `Animation.snappy` | iOS 17.0 | compiles at `-target arm64-apple-ios13.0` |

Both compile at every target down to 13.0. The shim was removed, and the
23 call sites it had rewritten are back to the originals.

The lesson is cheap to state and was not cheap to learn: **documented
availability is not compiler-enforced availability.** Several of the newer
SwiftUI and concurrency conveniences are `@_alwaysEmitIntoClient` or
`@backDeployed`, which means the implementation is inlined into the client and
the "iOS 17.0+" in the docs describes when the symbol was *added*, not the
floor it can be deployed against. A grep for known-new API names will flag all
of these as blockers and be wrong about most of them. The authority is
`swiftc -typecheck -target arm64-apple-ios<N>`, which is one command on the
runner and settles it in seconds — with a control case alongside it
(`.scrollTargetBehavior` is genuinely iOS 17 and genuinely errors) to prove the
target is being honoured at all.

## What actually changed

### Built-in StikJIT is out of the bundle

`project.yml` on this branch builds no `HuskJITHelper` and embeds no
`StikJIT.framework`. Both are Built-in StikJIT, which needs iOS 26: the
helper's own deployment target is 26.0 and the vendored framework declares
`MinimumOSVersion 17.4`.

Leaving them in is not free. `installd` validates nested bundles, and an app
extension whose `MinimumOSVersion` is above the running OS is at best ignored
and at worst an install failure whose message — "requires a newer version of
iOS" — names nothing useful. On a jailbroken device much of that validation is
bypassed, which makes it a risk that might or might not appear rather than one
that shows up immediately. Neither can do anything on iOS 16 regardless.

`JITBuiltIn.swift` still compiles in; `HuskBuiltInJIT.unavailableReason`
already returns *"Built-in JIT needs iOS 26 or later. Use StikDebug instead"*,
and `HuskJITHelper/HuskJITMessages.swift` is still a source of the app target
so the request types it needs are present. `scripts/package_ipa.sh` used to
*require* the helper and the framework and would have refused every IPA this
branch can produce; those three checks are now behind `HUSK_BUILTIN_JIT=1`.

### The checked-in project is now wrong on purpose

`src/app/Husk.xcodeproj/project.pbxproj` is tracked, and it is a build artefact
of `project.yml` that nothing on this branch has regenerated. It still contains
the `HuskJITHelper` target at deployment target 26.0 and the
`StikJIT.framework` link. `package_ipa.sh` regenerates the project before every
build, so this does not matter in practice — but it used to *warn* and carry on
when XcodeGen was missing, which here would have quietly built the bundle this
branch exists to avoid. It now exits instead.

### One deployment-target knob, and a check that it held

`HUSK_MIN_IOS` (default 16.4) is now read by `build_ios.sh`,
`build_angle_ios.sh`, `build_moltenvk_ios.sh` and `build_rppairing_ios.sh`, and
the workflow exports it to `xcodebuild` as well. Before this, four scripts
carried four independently-edited values: 16.0, 16.4, 16.4, and whatever
MoltenVK picks for itself.

`scripts/check_min_ios.sh` then proves it, across the app binary, every loose
dylib, every embedded framework and every app extension. This earns its own
step because a deployment-target mismatch is the one kind of iOS 16 breakage
that survives the entire pipeline: it compiles, it packages, it installs, and
then dyld refuses the library at launch with a message naming a path and no
version — indistinguishable from the missing-library failure that
`package_ipa.sh`'s validation was written for in the first place.

MoltenVK is the live case. `make ios` offers no flag for the deployment target
and picks its own; the script now exports `IPHONEOS_DEPLOYMENT_TARGET` into it,
and if that stops working `check_min_ios.sh` says so instead of the phone.

### The runner is an Intel Mac

`scripts/build_gpu_ios.sh` hardcoded `/opt/homebrew/bin/meson` and
`/opt/homebrew/bin/ninja`. That is the Apple Silicon Homebrew prefix; the Mac
behind this workflow is `x86_64` with Homebrew in `/usr/local`, where those
paths do not exist. libepoxy and virglrenderer would have failed with "No such
file or directory" several hours into a clean build, long after everything
cheap had already succeeded. Both are now found on `PATH`.

Two related facts about that machine, both handled in the workflow: Homebrew is
not on the `PATH` a non-interactive shell gets there, and `rustup` is not
installed at all.

## Why 16.4 and not 16.0

16.4 is a floor for the **Emulation** path, not a preference.

`scripts/build_angle_ios.sh` clears WebKit's availability overlay, which
surfaces the annotations it was suppressing — all of the form
"`MTLPixelFormatBC1_RGBA` is only available on iOS 16.4". Those are real: the
BC pixel formats arrived in 16.4, and below it ANGLE fails to build rather than
merely misbehaving. ANGLE is EGL/GLES for virglrenderer, so no ANGLE means no
GPU for the Android guest.

The script clamps rather than failing, so lowering `HUSK_MIN_IOS` below 16.4
builds an app that runs on 16.0 with a GL stack that still requires 16.4.
**That is not a configuration to ship** without also gating Emulation at
runtime. The Translation Layer does not go through ANGLE and would be
unaffected — which is the shape a 16.0 port would take, if it is ever wanted.

## Running a build

```sh
gh workflow run "Build (iOS 16)"                   # build, attach Husk.ipa to the run
gh workflow run "Build (iOS 16)" -f release=true   # ...and publish an ios16-v* prerelease
gh workflow run "Build (iOS 16)" -f deployment_target=16.5
gh workflow run "Build (iOS 16)" -f rebuild_deps=true   # throw away build/ first (hours)
```

Pushing an `ios16-v*` tag does the release form. Nothing runs on a plain push.

Two things about the workflow are deliberate and should not be undone:

- **`clean: false` on the checkout.** On a self-hosted runner `actions/checkout`
  reuses the workspace and otherwise runs `git clean -ffdx`, which deletes
  `build/`, `third_party/` and `guests/` — all three gitignored, and between
  them the cross-compiled QEMU, the WebKit sparse clone ANGLE is built from,
  MoltenVK's fetched dependencies and a 1.1 GB guest image. That is the entire
  multi-hour build, discarded before every run, with no `actions/cache` to fall
  back on. The build scripts are stamped and incremental; keeping the tree is
  what makes a warm run minutes instead of hours.
- **`timeout-minutes: 360`.** A cold tree cross-compiles QEMU and its five
  dependencies, ANGLE, libepoxy, virglrenderer and MoltenVK before it reaches
  the app.

### Testing without the round trip

The runner is reachable directly over SSH, which is how the compile checks above
were run. A type-check needs nothing but Xcode:

```sh
SDK=$(xcrun --sdk iphoneos --show-sdk-path)
cd src/app && swiftc -typecheck -target arm64-apple-ios16.4 -sdk "$SDK" \
  -swift-version 5 -import-objc-header Husk/HuskBridge.h \
  Husk/*.swift HuskJITHelper/HuskJITMessages.swift
```

That answers "does it compile for iOS 16" in seconds, without QEMU, ANGLE,
MoltenVK or a guest image — which is worth knowing, because the full
`ci_build.sh` is hours and most iOS-version questions are settled by the
type-checker.

## The runner needs about 25 GiB free

A clean build wants room for QEMU's source and build tree, the WebKit sparse
clone ANGLE is built from plus its archive, MoltenVK's `fetchDependencies`
building SPIRV-Cross, SPIRV-Tools and glslang, a Rust target directory and
DerivedData. A warm tree needs around 5.

The first attempt at this build died in `brew install qemu` with
`Errno::ENOSPC: No space left on device`, on a runner with **3.0 GiB free of
75**. ENOSPC surfaces wherever it happens to land -- a brew source build, a
ninja link, an xcodebuild archive -- and the message names the tool rather than
the disk, so it reads as a toolchain problem and not a full volume. The
workflow now checks up front and fails with the numbers instead.

On that machine the space is mostly two mounted simulator runtimes (iOS 26.5
and iOS 16.4, about 15.6 GiB between them) plus `~/Library/Developer`. The iOS
26.5 one is load-bearing for a *different* project's CI, which runs
`xcodebuild test` against a simulator; Husk cannot use a simulator at all,
since QEMU and ANGLE are built for `iphoneos` only.

## Still unverified

1. **A full `ci_build.sh` to an installable IPA.** Not reached: the runner ran
   out of disk before the build started, and freeing it was out of scope. The
   compile checks above cover the app's own sources; nothing has yet exercised
   the cross-compiled stack around them, `package_ipa.sh`'s validation, or
   `check_min_ios.sh` against real binaries.
2. **Installability of the trimmed bundle.** Removing the extension is meant to
   *reduce* install risk; it also changes the bundle shape from the one the
   shipped IPAs have, and `package_ipa.sh`'s validation is the only thing that
   has looked at it.
3. **Whether `/var/jb` is the right probe** for the jailbreak actually in use —
   cosmetic if wrong, per above.
4. **Memory.** `com.apple.developer.kernel.increased-memory-limit` and
   `extended-virtual-addressing` are both honoured on iOS 16, and properly so
   on a jailbroken install, so the 512 MiB JIT region and the guest RAM block
   should map as they do on 26. Husk probes the address space at startup and
   sizes the guest to what actually maps, so the failure mode is a smaller
   guest rather than a crash.
